# v2 說明：權限層

v1 的模型想做什麼就做什麼，連 `rm -rf` 或讀 `../.env` 都不會被攔。v2 在「模型說要呼叫工具」和「harness 真的動手」之間插一道守門員。loop 的骨架沒變，只多一步判定；程式在 `agent.py` 的「權限層」區段（`check_permission`、`ask_user`、`authorize`）。

## 在 loop 中的位置

```
模型回 tool_use
      │
      ▼
check_permission(name, args) ──► (decision, reason)
      │
      ├─ allow ─────────────────────────► execute_tool ─► tool_result
      ├─ ask ──► ask_user ── y / a ─────► execute_tool ─► tool_result
      │                  └─ n ─────────► tool_result(is_error)「使用者拒絕了…，理由：…」
      └─ deny ──────────────────────────► tool_result(is_error)「權限層拒絕：…」

同一則回應裡，第一個被拒絕（n 或 deny）之後，後面的 tool_use 不經過上面任何一步：
      └─ 同批連帶略過 ──────────────────► tool_result(is_error)「因為同一批中前面的 X 操作被拒絕…」
                                                │
                       全部 tool_result 放進同一則 user 訊息 → 下一輪模型看得到
```

每個判定都寫一行 log：`{"turn", "permission": {id, tool, input, decision, answer, reason}}`。

## 規則表

| 工具 | 條件 | 判定 |
| --- | --- | --- |
| read_file / write_file / edit / grep | `path` 解析後（含絕對路徑、`..`、symlink）不在 WORKDIR 內 | deny |
| glob | `pattern` 是絕對路徑或含 `..` | deny |
| read_file / grep / glob | 通過路徑檢查 | allow |
| write_file / edit | 通過路徑檢查 | ask |
| bash | 切段（`&& \|\| ; \|`）後，任一段含 `[A-Za-z0-9 _./=:,+-]` 以外的字元（引號、`$`、`~`、`*`、`?`、重導向、子 shell、單一 `&`、換行、NBSP 與其他控制／非 ASCII 字元） | ask |
| bash | 任一 token 是絕對路徑（含 `--opt=/x`）或含 `..` 片段；`cd` 不是剛好一個參數 | ask |
| bash | 每段第一個字都在白名單（`pwd ls cat head tail wc echo grep diff cd true which`） | allow |
| bash | 其他（python、pytest、find、env、rm、mv、curl、pip、git、sudo…） | ask |

- 白名單只放「讀取、列出」類指令。`python`／`pytest`／`find`／`env` 已移除：能跑腳本就能做任何事，字串規則擋不住，一律 ask。
- 回 `a`：write_file / edit 記工具名，本 session 之後該工具的 ask 變 allow（路徑限制仍在）。**bash 只記完全相同的指令字串**（`SESSION_ALLOW` 存 `("bash", command)`），換一條指令仍會問。`SESSION_ALLOW` 在模組層級，`/reset` 不清——權限屬於 session，不屬於對話。
- `PERMISSION_MODE=allow_all`（讀取時 `strip().lower()`，`Allow_All` 也有效）：ask 全部放行，但路徑 deny 仍然生效。
- bash 沒有 deny 規則，最多到 ask。輸入 EOF（沒人可以問）視為拒絕。
- `check_permission` 若丟例外（例如路徑含 NUL），`authorize` 一律判 deny：「參數無法判斷（…）」。
- symlink：`grep` 遞迴時略過 symlink 檔與目錄；`glob` 過濾掉 resolve 後不在 WORKDIR 內的項目；read_file／write_file／edit 靠 `_inside` 的 resolve 擋下。

## 同批連帶略過

同一則回應裡的多個 `tool_use` 通常是同一個計畫。第一個被拒絕（使用者回 n，或權限層 deny）之後，同批**後面**的 `tool_use` 不再詢問、也不執行：`tool_result` 回 `is_error`「因為同一批中前面的 X 操作被拒絕，這個操作沒有執行」，終端印「⏭ 略過」，permission log 記 `decision: "skipped"`（`answer` 為 null，仍帶 `id`）。拒絕**之前**已執行的步驟保留真實結果，沒有拒絕時行為不變。每個 `tool_use` 仍有配對的 `tool_result`，全部在同一則 user 訊息。

怎麼發現的：真實測驗（`evidence/logs/v2-run2-reject.jsonl`）中，模型一次送出 3 個互相依賴的 `tool_use`：edit reports.py、edit check.py、bash 跑 check.py。當時權限層逐一獨立詢問，使用者拒絕第 1 個、核准第 2 個，結果 check.py 改了而 reports.py 沒改，檔案停在半套狀態。拒絕其中一步，就代表整個計畫要重想。

剩下的限制：不能回滾。拒絕之前已經執行的步驟（例如批次中前面的 edit 已核准）不會被復原，模型要靠它們真實的 `tool_result` 自己判斷現況。

## 對應 Claude Code

| 這裡 | Claude Code |
| --- | --- |
| allow / ask / deny | permissions 的 allow / ask / deny 規則 |
| 回 `a` | 「Yes, and don't ask again this session」（bash 這裡只記完全相同的指令） |
| `PERMISSION_MODE=allow_all` | `--dangerously-skip-permissions` |
| 路徑限制 | 工作目錄範圍限制 |
| 沒做 | OS 層 sandbox（檔案系統／網路隔離）、規則設定檔、依指令前綴記住的規則 |

## 為什麼拒絕要回成 tool_result

1. 配對規則：每個 `tool_use` 都必須在下一則 user 訊息有對應 id 的 `tool_result`，否則 API 回 400。拒絕不是「跳過」，一樣要回一個結果。
2. 模型需要回饋：沒有結果它不知道發生什麼事；有結果（`is_error` 加上理由），它才有機會換方法。

## 刻意不在 system prompt 提示的觀察實驗

`SYSTEM_PROMPT` 沒有寫「被拒絕時要換方法」。要觀察的是：只靠 tool_result 裡那句「使用者拒絕了…理由：…這個操作沒有被執行」，模型會不會自己調整（改列計畫、換工具、問使用者），還是原樣重試。若表現不好，下一步才是對照實驗：在 prompt 或拒絕訊息加一句指引，看差異。

## 已知限制

bash 沒有被真正隔離，這裡只是字串判斷，不是安全邊界。被使用者核准過的腳本（write_file 寫、使用者按 y，再用 bash 跑並核准）可以做任何事；WORKDIR 內指向外部的 symlink 也可能被 `cat` 讀到。真正的防線是 OS 層 sandbox，所以仍然只在丟棄式資料夾跑。

另一個 harness 難題：同一則回應有多個 `tool_use` 時，工具是依序「詢問、執行」的。若第 1 個已經執行（寫了檔），在第 2 個的詢問時按 Ctrl-C，第 1 個的副作用不會回滾，而 `close_dangling` 為了維持配對，會替所有沒結果的 `tool_use` 補「工具未執行」——對第 1 個而言與事實不符，下一輪模型會以為它沒做過。這個沒修：要正確就得記錄每個工具實際的執行狀態、中斷時補真實結果，會讓程式變複雜，先當作已知限制。

## 紅方找到的繞過與教訓

最初的 `_bash_rule` 用「白名單第一個字＋擋幾個危險旗標」，紅方實測的代表例子：

1. 白名單指令讀 WORKDIR 外：`cat ../.env`、`cd ~; cat .env`、`cat $HOME/.env`、`cat ../.e*`、`ls -R /`——路徑 deny 只管檔案類工具，bash 完全沒檢查。
2. 分隔符漏洞：`ls\nrm -rf x`、`ls & rm x`——規則只切 `&& || ; |`，bash 卻把換行與單一 `&` 也當分隔。
3. 白名單內的指令能執行別的程式或寫檔：`env rm -rf x`、`find . -fprint ../x`、`python3 evil.py`、`pytest -p evil`。
4. 空白字元不一致：NBSP、`\x0b`、`\x0c` 讓 Python 的 `str.split` 與 bash 切出不同的字。
5. 狀態與例外：對 bash 回 `a` 後所有 bash（含 `rm -rf`）都放行；路徑含 NUL 讓 `resolve` 丟 ValueError 使 REPL 崩潰；grep／glob 跟著 symlink 讀到 WORKDIR 外。

教訓：從黑名單思維轉到白名單思維。黑名單（列舉危險指令與旗標）永遠列不完，每補一個洞，就有另一種寫法；而且「規則看到的字串」和「shell 實際解讀的字串」只要有一點不一致就是洞。現在改成只放行「一眼看得出安全」的：字元集先限縮到無歧義的子集，再比對白名單與路徑，其餘全部交給使用者判斷。誤判的代價只是多問一次（ask），漏判的代價是被繞過。同理，「記住使用者的同意」的範圍要盡量窄（只記完全相同的指令），判斷出錯時要預設拒絕（例外一律 deny）。

## 怎麼跑完成標準測驗

完成標準：拒絕一次後，模型收到「被拒絕」的回饋並改走別的路。

```bash
rm -rf sandbox/mini_repo && cp -r fixtures/mini_repo sandbox/
.venv/bin/python agent.py "把 mini_repo/shop/reports.py 裡 receipt_text 的報表標籤（大量折扣、優惠券、會員折扣、運費、總額等）改成英文。"
```

模型第一次 edit 時會被問：回 `n`，理由填「不要直接改檔，先把你打算怎麼改列給我看」。之後它若列出計畫，再回 `y`（或 `a`）讓它改。跑完：

```bash
.venv/bin/python scripts/summarize_log.py
```

注意（混淆）：若回 `n` 時填了理由（上面建議的「先把你打算怎麼改列給我看」），模型照理由做只能證明「模型會讀拒絕理由並照辦」，不能證明「光靠被拒絕就自己換方法」；後者要回 `n` 且理由留空才測得到（第 2 次真實測驗沒測到，n=1）。

「v2 完成標準判定」五項（skipped 不算被拒絕，第 1、2、4 項只看 n 與 deny）：
1. 至少一次 ask 被回 n（程式判定）。
2. 被拒絕後，下一個工具呼叫不是同工具＋同參數（沒有原樣重試）。
3. 被拒絕後模型有後續動作或文字回覆；會印出它被拒絕後的第一段 text，**需人工確認**是否真的「改走別的路」（例如改列計畫給你，而不是換個說法再 edit 同一處）。
4. 沒有被拒絕的操作被原樣重試超過 1 次。
5. 同一輪中被拒絕之後的 tool_use 全部是 skipped（沒有被詢問或執行）；沒有這種情況時顯示 PASS（不適用）。修改前錄的 `evidence/logs/v2-run2-reject.jsonl` 對這項是 FAIL，正好證明判定有效。

這個任務不是修 bug，v1 的判定區塊可能 FAIL，忽略即可；v2 判定不受它影響。
