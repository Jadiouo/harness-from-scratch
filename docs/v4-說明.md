# v4 說明

v4 把「進階」功能一個一個加進來（記憶、TODO、subagent、hooks）。

## 1. 專案記憶（CLAUDE.md）

模型沒有跨 session 記憶：v0 踩過 `python` 不存在、v2 又踩一次，每次都要失敗一次才改 `python3`。v4 的做法是啟動時讀 `WORKDIR/CLAUDE.md`，附在 system prompt 後面。程式在 `agent.py` 的「專案記憶（CLAUDE.md）」區段（`load_memory`、`build_system`、`SESSION_SYSTEM`）。

行為：
- 只讀 `WORKDIR/CLAUDE.md`，不往上層找。專案根目錄那份是給開發者的 Claude Code 用的，不是給這個 agent。`CLAUDE.md` 若是 symlink 且解析後跑出 WORKDIR，拒載並印警告（否則外部檔內容會被送上 API）。
- 不存在 → 沒有記憶；超過 `MAX_MEMORY_CHARS`（4000 字）→ 截斷並附標記、印警告；讀不了（非 UTF-8）→ 印警告、不載入；空白檔視為沒有。
- 載入時印 `📒 已載入 sandbox/CLAUDE.md（N 字）`；REPL 的 `/memory` 印出本 session 載入的內容。

## 放在哪裡：system vs 第一則 user 訊息

| | system prompt（採用） | 第一則 user 訊息 |
| --- | --- | --- |
| compaction | 不受影響，自動保留 | 壓縮會把歷史換掉，要另外特別保留 |
| 簽章綁定 | 在綁定範圍內，所以必須凍結 | 屬於歷史，不能事後改寫 |
| 權重 | 模型通常較重視 system 的指示（假設，未驗證） | 和一般對話混在一起 |

選 system 的主因是 compaction：v3 的壓縮整段換掉歷史，放在 user 訊息就得多寫一套「壓縮時保留記憶」的邏輯。

## 為什麼 session 開始組一次、之後凍結

thinking 區塊的簽章綁定「system＋tools＋之前所有訊息」。session 中途重組 system（例如重讀 CLAUDE.md）會讓舊的 thinking 區塊失效，API 回 400（`The block is bound to a different conversation ... The system prompt differs`）。這就是 v3 第一次真實測驗摘要請求踩到的問題（見 `docs/PROGRESS.md` 的「摘要請求 400」）。

所以 `main()` 啟動時只組一次 `SESSION_SYSTEM`，主對話與 compaction 的摘要請求都經過 `build_request`，拿到同一份。`/reset` 也不重新載入（system 屬於 session，不屬於對話）。代價：session 中途改 CLAUDE.md，要下個 session 才生效。

## 和 Claude Code 的比較（僅比較，未在本專案驗證）

- Claude Code 從 cwd 往上讀多層 CLAUDE.md。
- 有使用者層級的 `~/.claude/CLAUDE.md`。
- 子目錄的 CLAUDE.md 在用到那個目錄的檔案時才載入。
- 有 `/memory` 指令（用來編輯記憶檔；我們的 `/memory` 只是顯示本 session 載入的內容）。

## 驗證實驗

```bash
cp fixtures/memory/CLAUDE.md sandbox/CLAUDE.md
.venv/bin/python agent.py "建立 hello.py 並執行"
.venv/bin/python scripts/summarize_log.py
rm sandbox/CLAUDE.md   # 做完移除，避免影響其他測驗
```

預期（實測相符，見 `docs/PROGRESS.md`「v4-1 真實測驗」）：第一次 bash 就用 `python3`，不再出現 exit 127；`summarize_log.py` 的「v4-記憶判定」三項：1. 每個 request（含摘要請求）的 system 與第一個相同；2. 第一次含 python 的 bash 指令用 `python3`；3. 印出載入的記憶前 200 字。對照組是同一版程式、只是 `sandbox/` 裡沒有 `CLAUDE.md` 的 `evidence/logs/v4-mem-control.jsonl`：第 2 輪用 `python` 失敗、第 3 輪才改 `python3`，共 4 輪（有記憶組 2 輪）。

另外，`summarize_log.py` 的 v2 判定區塊改成只在 log 有「使用者回 n」或權限層 deny 時才印；沒有拒絕時第 1、3 項必然 FAIL，是顯示問題不是行為問題。

## 2. TODO 工具

程式在 `agent.py` 的 `todo_write`、`render_todos`、`TODOS`，以及壓縮區段的 `TODO_PREFIX`。工具 `todo_write` 的 input 是 `{"todos": [{"content": ..., "status": "pending" | "in_progress" | "completed"}]}`。

### 為什麼整份取代
每次呼叫都交整份清單，直接取代舊的（空陣列 = 清空）。模型不用追蹤 id，也不會出現「刪了不存在的項目」「改到一半」這類增刪改不一致。代價是清單長時每次都要重講一遍，但 TODO 清單通常不超過十幾項。格式錯、status 不合法、content 空白、多餘欄位、content 含換行（會破壞 `【目前 TODO】` 區塊一行一項的格式）、同時多於一個 `in_progress` 都回 `is_error`，不默默修正（模型要看到錯誤才知道清單沒生效）；唯一的正規化是 content 前後空白會被 strip。上限 50 項、每項 content 200 字，超過一樣 `is_error`（理由：清單每次壓縮都整份重放）。驗證失敗時舊清單不動。

`TODOS` 屬於 session：REPL 沒有 `/reset` 時會延續到下一個任務，這是刻意保留的（與 Claude Code 相同，僅比較）；模型下一個任務會用整份取代覆蓋。

### 為什麼狀態放 harness
清單存在模組層的 `TODOS`，不靠模型記、也不靠對話歷史。v3 的壓縮會整段換掉歷史，放在歷史裡的清單會跟著被摘要改寫；放在 harness，壓縮、`/reset`、`/todo` 都有單一的事實來源。`todo_write` 不碰檔案，權限層直接 allow（ask 模式也不問）。

### 壓縮時為什麼另附清單
v3 觀察到壓縮後模型會重讀已經改完的檔案（見 `docs/PROGRESS.md` 的 v3 失憶偵測），因為摘要是模型寫的，可能漏掉進度。所以壓縮後那則 user 訊息，若 `TODOS` 非空，在摘要之後多附一個 `【目前 TODO】` 區塊。這個區塊每次由 `TODOS` 重新產生，`user_texts` 會跳過它，連續壓縮只會有最新一份。compaction 的 log 行也帶 `todos`（壓縮當下的清單），事後才能檢查。

### 為什麼只靠工具描述引導
system prompt 刻意不提 TODO。這是對照實驗設計：v1 的經驗是工具描述寫得好，模型就會用對；這裡要看光靠描述，模型會不會在長任務自發先列清單、邊做邊更新。如果不會，才有理由去加 system prompt 說明，而且有了「沒加時的表現」可以比。TOOLS 在 session 內固定不變（thinking 簽章綁定 tools），所以 `todo_write` 是固定的一員，不動態增減。

### 和 Claude Code 的比較（僅比較，未驗證）
- Claude Code 的 TodoWrite 同樣是整份清單取代、同樣有 pending / in_progress / completed 三種狀態。
- 它的使用時機主要靠工具描述與 system prompt 的說明；我們只用工具描述。
- 它的清單怎麼在壓縮後保留，這裡沒有驗證。

### 實驗跑法與預期
跑法見 `fixtures/README.md` 的「v4-TODO 實驗」（沿用 v3 docstring_repo，任務句不提 TODO）。

判定腳本只採計成功的 `todo_write`（以 `tool_result` 行判斷，失敗或被同批略過的不算）。第 3 項：最後一次成功呼叫若是空陣列（清除，合法收尾），改看最後一份非空清單。第 4 項：沒有「壓縮當下已有清單」的 compaction 時顯示「不適用」、不計入全部通過；有的話要求 compaction 的 `todos` 等於當時最新成功清單。已知漏洞：第 1 項「先規劃再動手」只看 `edit`／`write_file`，bash 寫檔（`sed -i`、`>` 重導向）不算。

預期（**實測與此不同**：只靠工具描述時 `todo_write` 0 次，system prompt 補一句才出現，見 `docs/PROGRESS.md`「v4-2 真實測驗」）：
- 模型第一個動作附近就呼叫 `todo_write`，之後隨進度更新；`summarize_log.py` 的「v4-TODO 判定」四項通過。
- 壓縮後下一輪較少重讀已改檔案（與 v3 同任務的 `reread` 次數比較）。
- 也可能模型完全不用；那就是這個實驗的結果之一，腳本會印「⚠ 長任務但沒用 TODO 工具」。

## 3. subagent（task 工具）

程式在 `agent.py` 的「subagent」區段（`run_subagent`、`run_task`、`SUBAGENT_SYSTEM`、`SUB_TOOLS`），工具 `task` 的 input 是 `{"description": 3-8 字標題, "prompt": 給 subagent 的完整指示}`。

### 為什麼開一段新對話
目標是「主 agent 把搜尋整個 repo 丟出去，自己的 context 保持乾淨」。subagent 的 messages 是全新的（只有一則 user = prompt），它每次 grep、read_file 的結果都留在**它的**歷史裡，結束就丟掉；主對話只多一則 `tool_result`，內容是它最後那段結論文字。主對話之後每一輪都要重送整段歷史，所以少塞的每個字元會在後面每一輪都省一次。代價是 subagent 看不到主對話，`prompt` 必須自足（工具描述有寫），而且主對話只拿到結論、看不到證據，細節遺失就補不回來。

### 唯讀、不遞迴
`SUB_TOOLS` 從 `TOOLS` 篩出 `read_file`、`grep`、`glob`（同一份定義，不另寫）。沒有寫入工具，所以派出去的搜尋不可能改壞東西；沒有 `task`，所以不會遞迴開出一串 subagent。subagent 的每個工具呼叫仍經 `check_permission`（路徑跑出 WORKDIR 照樣 deny）；如果意外得到 ask 或 deny，一律當拒絕回 `is_error`，**不在 subagent 裡跳出 input 詢問**（使用者看不到它在做什麼，問了也不知道在問什麼）。呼叫 `SUB_TOOLS` 以外的工具也回 `is_error`。主對話裡 `task` 本身直接 allow（內部只有唯讀工具）。

### 為什麼 system/tools 可以和主對話不同
thinking 簽章綁定的是「同一段對話」的 system＋tools＋之前所有訊息（見第 1 節，v3 摘要請求踩過 400）。subagent 是另一段獨立的對話，簽章各自綁定，所以它用自己的 `SUBAGENT_SYSTEM` 和 `SUB_TOOLS` 不會 400。但**同一個 subagent 對話內**也要固定：它們是模組層常數、每一輪都傳同一份。`build_request(messages, system=None, tools=None)` 預設是主對話的值，主對話行為不變。

### 其他設計
- 輪數上限 `SUBAGENT_MAX_TURNS = 20`。不做 compaction：短命對話，到上限就停，比寫壓縮簡單。
- 結束方式：`end_turn` 回最後的文字；`max_tokens`／`refusal`／輪數用完回「已有的文字＋提前結束的原因」（沒有任何文字則 `is_error`）。結果套用既有的 `truncate`。
- subagent 的 usage **不碰** `LAST_USAGE`：壓縮判斷看的是主對話的長度，混進去會在不該壓縮時壓縮。
- Ctrl-C：往上拋，由 `run_turn` 的 `close_dangling` 補上 `task` 的 tool_result。subagent 的 API 例外（`anthropic.APIError`）由 `run_task` 接住：印 `[API 錯誤] subagent`、寫一行 error log，轉成這個 task 自己的 `is_error` 結果，同批其他工具照常完成（原本往上拋會丟掉同批已執行工具的結果，v4-3 審查後改）。
- SYSTEM_PROMPT 加了一句「需要大範圍搜尋、讀很多檔但只需要結論時，用 task 交給 subagent」。這是記取 TODO 實驗：只靠工具描述，模型不會自發使用（`docs/PROGRESS.md` 的 v4-2 第 1 次）。是否又需要這句話沒有對照過，先沿用這個經驗。
- 終端顯示：`→ task: <description>`，subagent 的每個工具呼叫縮排顯示 `  ↳ [sub] grep(...)`，結束印 `  ↳ [sub] 完成（N 輪，in=X out=Y tokens）`。

### log 與 summarize_log
subagent 的 request／response／tool_result 寫進同一個 log 檔，每行多 `"agent": "sub"` 與 `"sub_id"`（第幾次 task 呼叫）；主對話的行沒有這兩個欄位（所以舊 log 不用改，一律視為主對話）。`tool_result` 行多一個 `chars`（execute_tool 截斷後的字元數，`content` 只留前 300 字；實際讀到的可能更多，因此判定第 3 項偏嚴）。

`summarize_log.py` 的所有既有判定（v1／v2／v3／v4-記憶／v4-TODO）和每輪摘要**只算主對話的行**，否則 subagent 的不同 system 會讓「system 凍結」判定誤報、subagent 的 input_tokens 會汙染 v3 的峰值。每個 task 的 subagent 概要縮排印在該輪下面。新增「v4-subagent 判定」（log 有 sub 行才印）：
1. 主對話呼叫 task >= 1 次。
2. subagent 至少用過一次 grep／glob／read_file。
3. context 乾淨：task 回給主對話的字元數 < subagent 收到的工具結果總字元數（截斷後字元數；實際讀到的可能更多，因此偏嚴）的 20%（印出兩個數字與比例）。
4. 觀察（不判）：主對話 input_tokens 峰值、subagent 總 tokens、主對話在第一次 task 之後是否自己又 grep／glob／read_file（重做搜尋）。

20% 是憑感覺定的門檻，不是從資料推出來的；有實跑資料後再調。有 sub 行時不做 v1 的 mini_repo 修 bug 判定（這是唯讀任務）。

### token 怎麼算
subagent 花的 token **並沒有省**：它自己的每一輪也是整段歷史重送，總 tokens 可能比主對話自己搜尋還多。省的是**主對話**之後的 context：峰值 input_tokens 低，之後每一輪（以及觸發壓縮的時間點）都受益。所以實驗比較的是主對話的 input_tokens 峰值，不是總花費。repo 很小（mini_repo 約 405 行）時，這個好處可能不明顯。題目刻意保留這麼小（grep 兩次就能解）：重點是答案可客觀核對，比較的是主對話 context 有沒有被搜尋結果灌進來，不是 subagent 是否必要。

### 和 Claude Code 的 Task／Agent 工具比較（僅比較，未驗證）
- Claude Code 同樣是開獨立對話、只回傳最後的結果文字。
- 它有多種 subagent 類型（不同工具集與系統提示），也可以平行派多個；我們只有一種、一次一個。
- 它的 subagent 能用的工具範圍與權限怎麼繼承，這裡沒有驗證。

### 實驗跑法與預期
跑法見 `fixtures/README.md` 的「v4-subagent 實驗」：同一個唯讀題目（盤點 mini_repo 的折扣函式與呼叫關係，標準答案在 `fixtures/subagent_answer.md`）跑兩次，實驗組任務句結尾加「請用 task 工具派 subagent 去搜尋，你自己不要直接讀檔或搜尋。」，對照組加「不要使用 task 工具。」。

預期（實測大致相符，數字見 `docs/PROGRESS.md`「v4-3 真實測驗」）：實驗組主對話約 2-3 輪、input_tokens 峰值遠低於對照組，v4-subagent 判定 1-3 PASS；兩組答案都能指出 `loyalty_bonus` 沒人呼叫；實驗組的風險是 subagent 回報漏細節，主對話又無法驗證。小 repo 上總 tokens 不一定比較省。

## 4. hooks（使用者自己的程式，掛在工具前後）

程式在 `agent.py` 的「hooks」區段（`load_hooks`、`run_hooks`、`call_with_hooks`）。設定檔預設 `.agent/hooks.json`（環境變數 `HOOKS_FILE` 可改，專案根＝`agent.py` 所在目錄，已加進 `.gitignore`）：

```json
{"pre_tool_use":  [{"matcher": "bash", "command": "python3 my_check.py"}],
 "post_tool_use": [{"matcher": "edit|write_file", "command": "python3 fixtures/hooks/no_print_hook.py"}]}
```
`matcher` 是正規表達式，對工具名 **fullmatch**（`edit` 不會符合 `write_file`）。`/hooks` 列出已載入的。

### 和權限層的差別
權限層是**寫死的規則**（路徑要在 WORKDIR 內、bash 白名單），問的是「這個操作能不能做」；hook 是**使用者寫的程式**，問的是「這個操作合不合我們專案的規矩」（例如 shop/ 不准 print）。順序固定：權限層 → pre hook → 執行工具 → post hook。權限層拒絕的呼叫（deny 或使用者回 n，含同批連帶略過）不跑任何 hook，因為工具根本不會執行。hook 是使用者信任的程式，**不經權限層詢問**；但子程序的 env 與 bash 工具共用 `_clean_env()`（沒有 `ANTHROPIC_*`），另加 `AGENT_WORKDIR`。

### 約定
- stdin 收 JSON：`{"event", "tool", "input", "workdir"}`，post 另有 `"result": {"content"（前 2000 字）, "is_error"}`。cwd 是專案根，逾時 `HOOK_TIMEOUT = 30` 秒。
- exit 0：沒意見／放行。
- exit 2：pre 不執行工具，tool_result 是 `hook 擋下（<command 前 60 字>）：<stderr>`（`is_error`）；post 工具已執行，結果不變，content 尾端附 `[post_tool_use hook 回報]` 與 stderr。
- 其他 exit、逾時、無法執行：非阻擋錯誤，印 `⚠ hook 失敗` 並寫 log，**照常繼續**。
- 多個 hook 符合時依序跑；pre 有一個擋下就停（後面的不跑、工具不跑、post 也不跑）。
- pre 擋下算「被拒絕」：和權限層 deny／使用者拒絕一樣，同批後面的工具連帶略過（同一批是同一個計畫，不做一半）。我查了現有行為：deny 會設 `rejected`、觸發略過，所以 hook 擋下照做。post exit 2 不是拒絕（工具已執行），不略過。
- subagent 的工具呼叫（read_file/grep/glob）與主對話的 `task` 工具本身都走同一個 `call_with_hooks`，照 matcher 規則跑。subagent 裡 pre 擋下只回該工具的 `is_error`，沒有略過機制（它每個工具各自獨立回結果）。
- log：每次 hook 執行一行 `{"turn", "hook": {"event","tool","command","path"（input 的 path，沒有則 null）,"exit","stderr"（前 300 字）,"ms","decision"}}`，subagent 的另有 `agent: "sub"`、`sub_id`。

### 為什麼設定檔在 WORKDIR 外、而且只在啟動時讀
hook 能執行任意指令，如果模型能改它，等於模型能給自己任意執行權。設定檔放 WORKDIR 外：檔案工具的路徑 deny 擋得住模型改它；bash 想碰 `..`／絕對路徑會被權限層 ask。再加上只在 `main` 啟動時讀一次，所以 session 中途模型改了也不會生效（同 CLAUDE.md：一致、可預測；中途改要重啟）。格式錯誤時印警告、**整份不載入**，不做部分載入，免得使用者以為規則都在、其實只有一半。限制：`bash` 的 ask 被使用者放行（或 `allow_all`）後，仍可能改到設定檔；這不是安全邊界。另外，設定檔只在啟動讀，但 hook **腳本**每次執行都重新讀：若使用者用 `allow_all` 或放行能寫專案根的 `bash`，模型可以改腳本而影響 hook 行為。

### fail-open 的取捨
hook 自己壞掉（打錯字、缺套件、逾時）時選擇繼續而不是擋下：否則一個壞 hook 會讓整個 agent 停擺。風險是「檢查默默失效」，所以一定印警告並寫 log（`decision: "error"`）。要 fail-closed 的 hook 自己在腳本裡處理例外並 exit 2。

### post hook 回報為什麼不設 is_error
工具確實成功了，hook 只是補充意見；設 `is_error` 會讓「工具失敗」和「規則違反」混在一起。這是一個**觀察點**：回報只附在 content 尾端，模型會不會自己注意到並修正？`summarize_log.py` 的「v4-hooks 判定」看 exit 2 之後模型下一步做了什麼。

### 安全提醒
hook 以**你的使用者權限**執行任意 shell 指令，沒有 sandbox、沒有詢問。只放你自己寫、自己讀過的指令；不要從別人給的專案複製 `.agent/hooks.json` 就跑。

### 和 Claude Code hooks 的比較（僅比較，未驗證）
- 事件種類更多（不只工具前後，還有使用者送出訊息、結束、壓縮等）；我們只做 pre／post 兩個。
- 同樣有 matcher；exit 2 同樣是「阻擋並把 stderr 回饋給模型」的語意（細節以官方文件為準）。
- 它還支援用 JSON 輸出做更細的控制（例如決策、附加上下文）；我們只用 exit code ＋ stderr。
