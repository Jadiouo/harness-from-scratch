# v1 說明：讓它會找東西

v0 的模型只能「整檔讀、整檔寫」。v1 加三個工具並升級 `read_file`，目標是讓它走「先搜、再讀、再精準修改」，而不是整檔覆寫。v1 時的 `agent.py` 約 330 行（現在的 v4 約 960 行），loop 本身沒變，改的全在工具定義與工具執行器。

## 新增了什麼，對應 Claude Code 的哪個工具

| agent.py | 做什麼 | Claude Code 對應 |
| --- | --- | --- |
| `read_file(path, offset, limit)` | 讀檔，每行加行號，約 2000 行或 1 萬字元先到為止，並提示用 offset 繼續 | Read |
| `edit(path, old_string, new_string, replace_all)` | 精確字串替換，回傳修改處前後 3 行 | Edit |
| `grep(pattern, path, glob)` | 用 regex 搜內容，輸出 `路徑:行號: 內容`，最多 200 筆 | Grep |
| `glob(pattern)` | 依檔名樣式列檔案（支援 `**`），排序、最多 200 筆 | Glob |

另外 `write_file` 的描述改成「建立新檔或確實需要整檔重寫時才用」，SYSTEM_PROMPT 多一行工作順序（glob/grep → read_file → edit → bash 驗證）。

## 為什麼 edit 要求唯一匹配

- 避免改錯地方：`return x` 這種字串在檔案裡可能出現十次，沒有唯一性就會悄悄改到不該改的那處。
- 逼模型先讀：要寫出唯一、逐字相符的 `old_string`，它就得先看過檔案內容與前後文；憑印象改幾乎一定對不上。
- 失敗訊息要能指路：0 次、多次、新舊相同都回傳 `is_error`，並明講下一步該做什麼（先 read_file、加上下文或設 replace_all），模型才能自己修正。

## 行號被抄進 old_string 的坑

`read_file` 加行號後，模型很容易把 `    12\t    return x` 整行（含行號與 tab）複製進 `old_string`，結果檔案裡根本沒有這串字，`edit` 回 0 次匹配。預防方式不是改程式，而是工具描述：`read_file` 說「行號只是顯示用，不是檔案內容」，`edit` 說「不要包含 read_file 顯示的行號前綴」，0 次匹配的錯誤訊息再提醒一次。這正是 handoff 說的「改描述常比改程式有效」。

## 工具行為變更（審查後修正）

- **換行保留**：`edit` 與 `read_file` 用 `open(..., newline="")` 讀寫。原本的 `read_text()`/`write_text()` 會把 CRLF 全轉成 LF，改一行卻動到整個檔的換行。CRLF 檔裡模型給的多行 `old_string` 是 `\n`，所以 `edit` 會先換成檔案原本的換行再比對。
- **read_file 邊界**：空檔回「(空檔案)」；`offset` 超過檔尾、`limit < 1` 回 is_error；不是 UTF-8 的檔案（read_file／edit）回「不是 UTF-8 文字檔」。
- **grep**：`path` 不存在回 is_error；`glob` 同時比對檔名與相對路徑，`*.py`、`**/*.py`、`shop/*.py` 都能用。
- **glob**：描述寫明 `*.py` 只找 WORKDIR 根目錄，遞迴要用 `**/*.py`（模型最常踩的坑）。
- 路徑逃出 WORKDIR 仍然不擋，留給 v2 權限層。

### Harness 教訓：兩層截斷要對齊

`read_file` 本來只限制「行數」（2000 行），`execute_tool` 另有一層「字元數」通用截斷（1 萬字元，保留頭尾）。兩層各管各的，結果是：2000 行的大檔會先被字元截斷從中間砍掉，模型看到的是「開頭 + 截斷訊息 + 結尾」，中間幾百行不見，而 `read_file` 自己的「用 offset 繼續讀」提示正好在被砍掉的位置附近，要不就被砍、要不就指到錯誤的行。現在 `read_file` 自己累積輸出，接近上限（留 500 字元餘量）就在**行邊界**停下，結尾給「讀到第 N 行，檔案共 M 行，用 offset=N+1 繼續讀」，通用截斷永遠碰不到它。原則：工具若有自己的分頁機制，大小上限要由工具自己掌握；通用截斷只是最後一道保險，不該是分頁的實際行為。

## 怎麼跑完成標準測驗

```bash
rm -rf sandbox/mini_repo && cp -r fixtures/mini_repo sandbox/
.venv/bin/python agent.py "sandbox 裡的 mini_repo 執行 python3 check.py 會失敗，請找出原因並修好。"
.venv/bin/python scripts/summarize_log.py        # 預設看 logs/ 最新的檔；--repo／--fixture 可改路徑
```

每個新開的終端機都要重新 `export ANTHROPIC_API_KEY=...`（環境變數不會在視窗之間共用）；沒設的話 `agent.py` 會直接提示並結束，`summarize_log.py` 也會在 log 比 repo 舊或不是 mini_repo 測驗時以 exit 2 拒絕判定。

（`agent.py` 的 WORKDIR 就是 `sandbox/`，所以模型實際看到的路徑是 `mini_repo/...`。）fixture 是 13 個檔案、400 多行的小商店 repo，有好幾處長得很像的臨界值比較（運費、補貨、優惠券），但只有一處是錯的，`check.py` 的失敗訊息只描述行為（哪張訂單、預期多少、實際多少），不提示原因。正確答案不寫在文件裡，見 `tests/test_agent.py` 的 `test_fixture_fix_with_edit_gives_all_ok`。不要把 tests/ 給模型看。

`summarize_log.py` 結尾會自動判定，六項全部 PASS 才算通過：
1. 在 `sandbox/mini_repo` 實際執行 `python3 check.py`，輸出含 `ALL OK`。
2. `check.py` 與 fixture 的內容相同（沒偷改測試）。
3. 和 fixture 比對，只改了 1 個檔，且 diff 改動行數 <= 3（會印出 diff）。
4. 第一次成功的 `edit` 之前，有 `grep` 或 `glob`，且對被修改的檔案做過 `read_file`。
5. 沒有對 fixture 裡本來就有的檔案用 `write_file`（路徑先正規化）。
6. 工具參數與 bash 指令沒有碰 `fixtures/`、`tests/`、`docs/` 或含 `..` 的路徑（偷看答案偵測）。

另外「觀察」區列出 bash 裡的 `sed -i`、`cat >`、`grep`、`find` 等繞過專用工具的指令，只提醒、不判 FAIL。判定邏輯本身的測試在 `tests/test_agent.py` 的 `test_judge_*`。

## 3 個 v1 觀察實驗

1. 拿掉 SYSTEM_PROMPT 的工作順序那行，同一題重跑。預期：搜尋變少、更常直接 `read_file` 整個檔案，甚至用 `write_file` 整檔重寫；對照 summarize_log 的工具呼叫次數。
2. 把 `edit` 描述裡「不要包含行號前綴」那句拿掉。預期：模型偶爾把行號抄進 `old_string`，先吃一次「找不到 old_string」，下一輪才修正；這證明錯誤訊息回傳也有補救效果。
3. 把 `edit` 的唯一匹配檢查暫時拿掉（改成只替換第一處）。預期：遇到重複字串時悄悄改到第一處而非目標處，check.py 仍失敗，模型要多繞幾輪才發現；唯一性檢查的價值在這時才看得到。
