# v3 說明：上下文管理（compaction）

v2 的 loop 每輪都把整段歷史重送一次，任務一長 context 就會爆。v3 在 loop 每輪呼叫 API 之前多一道檢查：上一輪用掉的 tokens 超過門檻，就把整段歷史換成「摘要＋使用者原文」。程式在 `agent.py` 的「上下文管理（compaction）」區段（`needs_compaction`、`compact`）。

## 為什麼 context 會長

API 沒有記憶，harness 每輪都得把完整歷史（含每個 tool_result）再送一次。真實數字取自 `logs/v1-A-baseline.jsonl`（只有 6 輪的小任務）：

| 輪 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- |
| input_tokens | 2388 | 2735 | 3057 | 4818 | 8585 | 9173 |

第 6 輪的 input 是第 1 輪的近 4 倍，而且每讀一個大檔就跳一階。30 輪以上的任務會一路疊上去。

## 兩層防線

1. 單次輸出截斷（v0）：`MAX_TOOL_OUTPUT_CHARS`，擋住「一次灌爆」。
2. compaction（v3）：擋住「慢慢疊爆」。

```
        ┌──────────────────────────────────────────────┐
        ▼                                              │
  [壓縮檢查] ─► 呼叫模型 ─► tool_use? ─► 執行工具 ─► 結果寫回歷史
   上一輪 usage                  │ end_turn
   > COMPACT_AT_TOKENS?          ▼
     │是                       結束
     ▼
  另外呼叫一次 API 要摘要（tools 仍帶著、tool_choice=none）
  壓縮前： [user][asst][user:tool_result][asst]...[user:tool_result]   （幾十則）
  壓縮後： [user:標頭 | 原文1 | 原文2 ... | 摘要＋請接著完成任務]        （1 則、多個 text 區塊）
```

## 壓縮後訊息的區塊結構

壓縮後那則 user 訊息由多個 text 區塊組成，靠固定前綴辨認（常數在 `agent.py`）：

1. `【context 已壓縮】`：標頭。
2. 每段使用者原文一塊，前綴 `【使用者原文】\n`，後面是原文本身，逐字。
3. 最後一塊：前綴 `【先前工作摘要】\n`，後接摘要與「請接著完成任務。」

為什麼使用者原文要分塊、逐字保留：摘要是模型改寫的，使用者的話不能經過改寫；而且分塊加前綴之後，`user_texts()` 下次壓縮時才分得出哪些是原文（取前綴之後的部分）、哪些是上次的標頭與摘要（跳過）。早先把整段塞進一個區塊時，連續壓縮會把前一次的摘要當成使用者原文收進去，摘要一層一層疊上去。現在舊摘要會被新摘要取代。

## 為什麼不採「清掉舊 tool_result」

- 歷史只能往後加（v0 起的原則）：claude-opus-5-5 的 thinking 區塊綁定整段對話，改寫舊訊息會讓它們失效，部分帳號會直接 400。
- prompt cache 吃的是前綴：中間改一個字，後面全部 cache 失效。
- 所以改成整段換掉：新對話不含任何舊的 assistant/thinking 區塊，沒有「改寫」的問題。代價是換掉當下 cache 全失效一次。

## 比較（僅比較，未在本專案驗證）

- Claude Code：context 接近上限時自動 compact，也能手動 `/compact`；概念和這裡相同，細節（保留什麼、怎麼提示）未驗證。
- API 的伺服器端 compaction（beta `compact-2026-01-12`）：由 API 端代為壓縮，harness 不用自己呼叫摘要。
- context editing（`clear_tool_uses_20250919`）：清掉舊的 tool_use/tool_result，屬於「改歷史」路線，和這裡刻意避開的做法相反。

## 摘要的取捨

- 使用者原文原樣保留（`user_texts`）：摘要是模型改寫的，使用者的要求不能經過改寫。
- 摘要指示要求列出「已完成的檔案」與「剩下的檔案」：壓縮後模型最容易忘記進度。
- 可能的失憶：摘要漏寫的事就是沒發生過。壓縮後模型可能重讀已改好的檔案，甚至重做；`summarize_log.py` 第 6 項會列出來（觀察，不判 FAIL）。
- 摘要請求失敗（APIError）、沒有文字、或 `stop_reason` 不是 `end_turn`：印警告、不壓縮、loop 照常繼續。
- 摘要被截斷的風險：`max_tokens` 截斷的摘要會缺尾巴（通常正是「下一步」與「剩下的檔案」），採用它等於把歷史換成殘缺的記憶，之後無法挽回；拒絕（refusal）的回應更不是摘要。所以只接受 `end_turn`，其他一律不壓縮（歷史原封不動）。
- 冷卻：失敗後 `COMPACT_COOLDOWN_TURNS`（3）輪內不再自動嘗試，否則 usage 仍超標，每輪都白付一次失敗的摘要請求。`/compact` 手動不受冷卻影響，`/reset` 會清掉冷卻。失敗會寫一行 `compaction_failed` 到 log。
- 邊界：只在沒有未配對 tool_use 時壓縮（尾端是 user，或一輪結束後的 assistant）。`/compact` 在一輪結束後下，尾端是 assistant，所以也算邊界。

## log 的 tool_result 行

每個 tool_use 得到結果後（執行、拒絕、略過都算），`_loop` 寫一行 `{"turn", "tool_result": {"id", "tool", "is_error", "content"(前 300 字元)}}`。原因：壓縮會換掉歷史，之後下一輪 request 裡不再有舊的 tool_result，事後就查不到哪些 edit 成功過；這也符合「記錄一切」的原則。`summarize_log.py` 的失憶偵測靠它。

## 怎麼跑完成標準測驗

```bash
rm -rf sandbox/docstring_repo && cp -r fixtures/docstring_repo sandbox/
.venv/bin/python agent.py "docstring_repo 裡的函式都還沒有 docstring。請逐一讀過每個檔案，幫每個函式補上一行繁體中文 docstring，完成後執行 python3 check_docstrings.py 確認。"
.venv/bin/python scripts/summarize_log.py     # 舊 log 若沒有 compact_at，加 --compact-at N
```

詢問時第一次 edit 回 `a`，bash 的 `python3 check_docstrings.py` 回 `a`。REPL 內可用 `/compact` 手動壓縮、`/tokens` 看最近一次 input/output tokens。

判定項目：1. 工具呼叫 >= 30；2. 至少 1 次 compaction；3. 最後一次 compaction 後還有工具呼叫；4. `check_docstrings.py` 輸出 ALL OK 且沒被改；5. input_tokens 峰值 <= 門檻 x 2（門檻優先取 log 裡 compaction 行記錄的 `compact_at`，沒有才用 `--compact-at`；並列出每次壓縮前後）；6. 觀察：疑似失憶（壓縮前已成功 edit 的檔案，壓縮後又 read_file，且之後沒再成功 edit）、重複編輯（近似判斷）、壓縮後對已改檔案的 write_file／bash cat 存取。

門檻 `COMPACT_AT_TOKENS` 預設 8000，是故意設低讓測驗觸發（fixture 全部只有約 6.8k 字元，要能觸發 2 次以上壓縮）；真實 harness 會接近模型 context 上限才壓縮。

## 觀察實驗

1. `COMPACT_AT_TOKENS=4000`：預期壓縮次數變多、摘要失真累積，第 6 項重讀次數增加。
2. 拿掉 `SUMMARY_REQUEST` 中「已完成的工作（列出已處理的檔案）」與「尚未完成的工作（列出剩下的檔案）」：預期壓縮後模型重讀、甚至重做已補好的檔案，第 3、6 項變差。
3. 在 SYSTEM_PROMPT 加一句「context 可能被壓縮，開頭的摘要是你先前工作的紀錄」：預期更能直接接續、少重讀；這是目前刻意沒加的對照組。
