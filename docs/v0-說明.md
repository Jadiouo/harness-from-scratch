# v0 說明：最小 agent loop

`agent.py` 約 230 行，不用任何框架，迴圈手寫在 `run_turn`。模型本身不執行任何東西，harness 負責組 request、執行工具、把結果寫回歷史。

## 流程圖

```
 使用者輸入 (REPL / 命令列)
      │  add_user_text
      ▼
 組 request  ── build_request（system + tools + 全部歷史 + output_config）
      │
      ▼
 呼叫模型  ──► 寫 log（一輪一行）──► 整包 assistant 回應 append 進 messages
      │
      ▼
 看 stop_reason
   ├─ end_turn    ──► 結束，回 REPL
   ├─ max_tokens / refusal / 其他 ──► 印出訊息後結束（結束前 close_dangling 補齊歷史）
   ├─ pause_turn  ──► 再送一輪（v0 無 server tool，走不到）
   └─ tool_use    ──► execute_tool（本則回應所有 tool_use，依序）
                         │
                         ▼
          全部 tool_result 放進「同一則」user 訊息 append
                         │
                         └──► 回到「呼叫模型」（最多 MAX_TURNS 輪）

 任何結束路徑（return、API 例外、Ctrl-C）──► finally: close_dangling(messages)
```

## 為什麼需要 close_dangling

API 規則：assistant 訊息裡每個 `tool_use`，下一則 user 訊息必須有對應 `tool_result`；也不接受空的 assistant 訊息。一旦歷史違反，之後每次呼叫都回 400，session 就廢了。

最典型的例子是 `max_tokens` 截斷：模型寫到一半被截，回應可能已含 `tool_use` 區塊。`run_turn` 先整包 append 了 assistant，卻因 stop_reason 不是 `tool_use` 而直接結束，沒人執行工具、也沒補 `tool_result`，就留下孤兒 `tool_use`。Ctrl-C 發生在工具執行途中也是同樣結果。

`close_dangling` 在 `run_turn` 的 `finally` 裡執行：最後一則是空的 assistant 就移除；含 `tool_use` 就補一則 user，對每個 `tool_use` 回 `is_error` 的 `tool_result`。API 呼叫失敗（429／529／網路）則由 `except anthropic.APIError` 接住、印出後回 REPL，此時歷史尾端是 user，下一句會被 `add_user_text` 併進去。

## 區段 ↔ harness 角色 ↔ Claude Code 行為

| agent.py 區段（函式） | harness 角色 | 對應 Claude Code 的行為 |
| --- | --- | --- |
| `SYSTEM_PROMPT` | 系統提示 | Claude Code 內建的長 system prompt 與 CLAUDE.md 注入 |
| 設定常數 | 設定 | 模型、effort、權限模式等設定 |
| `TOOLS` | 工具定義（給模型看的說明書） | 每個內建工具（Read/Write/Bash）的 description 與 schema |
| `execute_tool`、`read_file`、`write_file`、`bash` | 工具執行器 | 真正讀寫檔、跑 shell；錯誤以 is_error 回報 |
| `truncate` | 輸出截斷 | 工具輸出過長時裁切，保護 context |
| `to_jsonable`、`new_log_path` | 紀錄 | transcript 紀錄，可事後回放 |
| `build_request` | request 組裝 | 每輪把歷史、工具、參數打包送出 |
| `run_turn`、`close_dangling` | agent loop | 「呼叫模型 → 執行工具 → 寫回」的主迴圈與 stop_reason 分派；結束時保證歷史合法 |
| `add_user_text`、`main` | REPL | 終端機互動、`/reset`、`/exit` |

## 怎麼跑

```bash
export ANTHROPIC_API_KEY=sk-ant-...        # 不要寫進程式碼
.venv/bin/python agent.py "建立 hello.py 並執行"   # 單次模式
.venv/bin/python agent.py                          # REPL
ls logs/                                           # 每個 session 一個 jsonl
```

log 每行是一輪：`turn`、`request`（model/system/tools/messages）、`response`。可用 `jq` 或 Python 逐行讀。可用環境變數 `MODEL`、`EFFORT`、`MAX_TURNS`、`WORKDIR`、`USE_FALLBACKS` 調整。工具只在 `sandbox/` 內以該資料夾為 cwd 執行；v2 權限層之前，不要讓它碰重要資料。

## 建議的觀察實驗

以下「預期」只是可能的現象，不是保證，請實際看 log 驗證。

1. **拿掉 system prompt 裡「一定要實際執行驗證」那句。** 預期：模型較可能寫完檔就回報完成，不再呼叫 bash，輪數變少。
2. **把 `bash` 的 description 改成只剩「run stuff」。** 預期：可能少用或誤用，例如用 write_file 想「執行」程式，或不知道非 0 exit code 只是回報。
3. **在 `execute_tool` 的錯誤回傳裡拿掉 `is_error`（或改成丟例外）。** 預期：拿掉 is_error 時模型仍可能從文字看出錯誤，但較不穩定；改丟例外則這一輪被中止（`finally` 的 `close_dangling` 會補 `tool_result` 讓歷史仍合法，但模型看不到錯誤內容，沒有自我修正的機會）。
4. **`MAX_TURNS=2` 並給多步驟任務。** 預期：印出「達到最大輪數」；歷史最後一則是 user（tool_result），下一次輸入的文字會附加進那一則，模型接著做，不會出 API 錯誤。
5. **叫它 `cat` 一個很大的檔案（或印 5 萬字）。** 預期：tool_result 中間出現「截斷了 N 個字元」，模型可能改用 head/grep 縮小範圍。
